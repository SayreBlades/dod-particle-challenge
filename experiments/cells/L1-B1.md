# B1 — the fused single-walk-step blueprint (demonstration)

> This document demonstrates the optimization framework end-to-end on one
> blueprint (B1). It shows the walk-file / cell-file structure, the
> declaration blocks, how cells compose, and how to build/run/verify. The
> framework's contracts (§10) and the death model (§7) are already landed;
> this is what a fully-declared blueprint looks like.

## The B1 blueprint

B1 fuses **math + decide + respawn** into walk 1 and keeps **render** as a
separate walk 2. No intermediates carry the death decision — the respawn
happens in-place, in the same walk that decided death:

```
walk 1: math + decide + respawn    (in-place; no scratch)
walk 2: render
intermediates: none
```

The five logical stages (§1) partition into two walks. This is the simplest
non-degenerate blueprint: one decision is made and consumed in the same walk,
and the render is unfused.

## The walk files

B1's walks live as composable files under `src/layouts/L1_aos_full/walks/`.
Each exports its step/render function **and** a `decl: WalkDecl` describing
itself (impl / schedule / parallel / variant). A cell composes a w1 file +
a w2 file — no code is duplicated between cells:

| walk file | role | impl | schedule | variant | golden |
|---|---|---|---|---|---|
| `w1-naive.zig` | math+decide+respawn | zig | auto | branchy | bit-exact |
| `w1-scalar.zig` | math+decide+respawn (de-vec) | zig | scalar | branchy | bit-exact |
| `w1-halide.zig` | math+decide+respawn (blend) | halide | scalar | blend | statistical |
| `w2-naive.zig` | render (r0 splat) | zig | r0 | none | — |
| `w2-opt.zig` | render (r1 splat) | zig | r1 | none | — |

The **variant** axis is what drives the golden class: `branchy` respawns
from the ordered spawn-RNG stream (bit-exact against the reference);
`blend` computes respawn values for all N every frame from a per-particle
hash RNG — a different model, so the golden is statistical (§6).

## The five B1 cells

Each cell file (`src/layouts/L1_aos_full/cells/`) is ~20 lines: a `cell_decl`
whose `walks` array pulls the decls from the walk files, plus `H.step =
w1.step` / `H.render = w2.render`. The cell name encodes the blueprint +
per-walk impl:

| cell | walk 1 | walk 2 | golden | what it isolates |
|---|---|---|---|---|
| `L1.B1.w1-naive.w2-naive` | zig/auto/branchy | zig/r0 | bit-exact | **the reference** (generates `golden/stage1.bin`) |
| `L1.B1.w1-naive.w2-opt` | zig/auto/branchy | zig/r1 | bit-exact | walk-2 schedule: r0 → r1 |
| `L1.B1.w1-scalar.w2-naive` | zig/scalar/branchy | zig/r0 | bit-exact | walk-1 schedule: auto → scalar |
| `L1.B1.w1-halide.w2-naive` | halide/scalar/blend | zig/r0 | statistical | walk-1 impl+variant: zig/branchy → halide/blend |
| `L1.B1.w1-halide.w2-opt` | halide/scalar/blend | zig/r1 | statistical | (above) + walk-2 r0 → r1 |

Every comparison's axis differences are enumerable from the declaration diff.
Example: `L1.B1.w1-naive.w2-naive` vs `L1.B1.w1-scalar.w2-naive` differs in
exactly one field — walk-1 `schedule: auto → scalar`. That is the honest
version of "vary one axis."

## Build, run, verify

```sh
# the reference cell (regenerates golden/stage1.bin + golden/frame.sha256)
zig build -Dlayout=L1 -Dstrat=B1.w1-naive.w2-naive -Dmode=bench -Doptimize=ReleaseFast
./zig-out/bin/dod-particles

# any B1 cell (verifies against the golden)
zig build -Dlayout=L1 -Dstrat=B1.w1-naive.w2-opt -Dmode=bench -Doptimize=ReleaseFast
./zig-out/bin/dod-particles

# the churn regime (q=0.5) — goldens skip loudly; the sim is a different one
zig build -Dlayout=L1 -Dstrat=B1.w1-naive.w2-naive -Dmode=bench -Ddeath=0.5 -Doptimize=ReleaseFast
./zig-out/bin/dod-particles

# regenerate the cell manifest from the declaration blocks
zig build manifests
cat experiments/cells/L1.md
```

Every bench run prints the cell declaration (the §6/§8 "never silent" rule):

```
=== Cell ===
  name:          L1.B1.w1-naive.w2-naive
  layout:        L1_aos_full
  blueprint:     B1 (math+decide+respawn | render)
  ordering:      identity
  intermediates: none
  walk1:         { impl: zig, schedule: auto, parallel: none, variant: branchy }
  walk2:         { impl: zig, schedule: r0, parallel: none, variant: none }
  golden:        bit_exact
```

## Golden behavior

- **bit-exact** (the three `w1-naive`/`w1-scalar` cells): trajectories are
  byte-identical to the reference. The golden is verified at q=0. At q>0 the
  golden is skipped (a different sim); the invariant suite (§10.6, Phase 1)
  is the correctness floor there.
- **statistical** (the two `w1-halide` cells): physics and respawn
  distributions are identical to naive, but trajectories diverge by design
  (per-particle hash RNG). The golden is skipped loudly, never silently.

## What is NOT here yet

- **Other blueprints** (B2: `halide_a`; B3: `par`, `halide_a2`) are still
  pending relabel — they build and run under their historical names but show
  as `pending` in the manifest. They get the same treatment when we move to
  them.
- **Parallel B1 cells** (B1 branchy data-parallel, B1 blend branchless) and
  the **invariant suite** (§10.6) are Phase 1.
- **No global winner.** B1's four+one cells are schedule/impl variants; the
  "best" is regime-dependent (§16.9). At natural churn (q=0) the branchy
  variant should win (rare branch, predicted); at high churn (q≈0.5) the
  blend/halide variant becomes competitive (death-rate-invariant). Measuring
  that is the death-rate sweep (Phase 1, Table B).
